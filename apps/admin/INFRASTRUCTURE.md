## 3. Provider Architecture

All global providers live in `app/layout.tsx`. The nesting order matters — each provider can only use context from providers wrapped around it.

```
ClerkProvider                  ← Auth context (must be outermost)
  └── AntdRegistry             ← Collects Antd CSS for SSR (prevents style flash)
        └── ConfigProvider     ← Antd theme tokens applied globally
              └── QueryProvider  ← TanStack Query client
                    ├── ApiAuthInjector  ← Sets up axios interceptors (needs Clerk context)
                    └── {children}       ← All pages render here
```

### Why this order?

- **ClerkProvider outermost** — every component that needs auth state (`useAuth`, `useUser`, etc.) must be inside ClerkProvider. This includes `ApiAuthInjector`.
- **AntdRegistry before ConfigProvider** — `AntdRegistry` captures the CSS generated by Antd during server rendering and injects it into the HTML `<head>`. If it wraps ConfigProvider, it captures the themed styles too.
- **QueryProvider inside Clerk** — TanStack Query hooks in components need both auth context (to fetch with auth) and the query client. Placing it inside Clerk means components can use both.
- **ApiAuthInjector inside ClerkProvider** — it calls `useAuth()` which requires ClerkProvider to be an ancestor.

## 4. Auth — Clerk

### How authentication works

```
Browser request
      │
      ▼
middleware.ts                ← runs before any page renders
      │
      ├── Public route? (/sign-in, /sign-up)
      │         └── Allow through
      │
      └── Protected route? (everything else)
                └── Clerk JWT present and valid?
                          ├── Yes → allow through
                          └── No → redirect to /sign-in
```

### Key files

**`middleware.ts`** — The gatekeeper. Runs on every request at the edge (before the server renders anything).

```typescript
const isPublicRoute = createRouteMatcher(["/sign-in(.*)", "/sign-up(.*)"]);

export default clerkMiddleware(async (auth, request) => {
  if (isPublicRoute(request)) return; // let sign-in/sign-up through
  await auth.protect(); // everything else requires auth
});
```

If `auth.protect()` finds no valid session, it redirects the user to `/sign-in` automatically.

**`app/(auth)/sign-in/[[...sign-in]]/page.tsx`** — Renders Clerk's pre-built sign-in UI. The `[[...sign-in]]` catch-all route is required by Clerk to handle its internal redirect flow (e.g. after email verification).

**`app/(auth)/sign-up/[[...sign-up]]/page.tsx`** — Redirects to sign-in. Sign-up is invite-only; new users are added via the Clerk dashboard (Organizations → Invite Member).

### Using auth state in components

```typescript
"use client";
import { useAuth, useUser } from "@clerk/nextjs";

// Get the current user
const { user } = useUser();

// Check a permission
const { has } = useAuth();
const canEditProducts = has({ permission: "org:products:edit" });

// Conditionally show UI
if (!canEditProducts) return null;
```

## 5. API Layer — Axios

### How API requests work

```
Component
    │ calls productApi.getAll()
    ▼
lib/api/product.ts           ← domain service function (you create these per feature)
    │ uses apiClient.get(...)
    ▼
lib/api/client.ts            ← base axios instance
    │
    ▼
ApiAuthInjector interceptor  ← automatically attaches Bearer token
    │
    ▼
NestJS API (NEXT_PUBLIC_API_URL)
```

### Key files

**`lib/api/client.ts`** — Creates a single axios instance used by all API service files. The `baseURL` is read from the `NEXT_PUBLIC_API_URL` environment variable — never hardcoded.

**`components/providers/api-auth-injector.tsx`** — A client component that renders nothing (`return null`) but sets up two axios interceptors when it mounts:

1. **Request interceptor** — Before every axios request, it calls `getToken()` from Clerk and attaches the JWT as `Authorization: Bearer <token>`. This happens automatically for every request — you never add the header manually.

2. **Response interceptor** — If any API call returns a `401 Unauthorized`, it redirects the user to `/sign-in`. This handles expired sessions globally.

```typescript
// What happens under the hood before every API request:
config.headers.Authorization = `Bearer ${await getToken()}`;
```

The interceptors are ejected (cleaned up) when the component unmounts, preventing memory leaks.

### Adding a new API service

Create a file per domain in `lib/api/`:

```typescript
// lib/api/product.ts
import { apiClient } from "./client";

export const productApi = {
  getAll: (params: QueryDto) => apiClient.get("/products", { params }),
  getById: (id: string) => apiClient.get(`/products/${id}`),
  create: (body: CreateProductDto) => apiClient.post("/products", body),
  update: (id: string, body: UpdateProductDto) =>
    apiClient.patch(`/products/${id}`, body),
  delete: (id: string) => apiClient.delete(`/products/${id}`),
};
```

## 6. Server State — TanStack Query

### Purpose

TanStack Query manages all server data: fetching, caching, background refetching, and mutations. It prevents duplicate requests and keeps the UI in sync with the API.

### Key files

**`lib/query-client.ts`** — A factory function (not a singleton) that creates a `QueryClient` with shared defaults. It's a function so each React tree gets its own instance (important for SSR correctness).

```typescript
// Default config applied to all queries:
staleTime: 60 * 1000; // data is "fresh" for 60 seconds — no refetch during this window
retry: 1; // retry failed requests once before showing an error
```

**`components/providers/query-provider.tsx`** — A client component that creates the QueryClient once (via `useState`) and provides it to the entire component tree. Using `useState` ensures the client is created only once per mount, not on every re-render.

### Using TanStack Query in a component

```typescript
"use client";
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { productApi } from "@/lib/api/product";

// Fetching data
const { data, isLoading } = useQuery({
  queryKey: ["products", "list", filters], // cache key — must be unique per request shape
  queryFn: () => productApi.getAll(filters),
});

// Mutating data (create/update/delete)
const queryClient = useQueryClient();
const mutation = useMutation({
  mutationFn: (body) => productApi.create(body),
  onSuccess: () => {
    // Invalidate the list cache so it refetches after a create
    queryClient.invalidateQueries({ queryKey: ["products", "list"] });
  },
});
```

## 7. UI — Ant Design + Tailwind

### Division of responsibility

| Use case                                       | Use                 |
| ---------------------------------------------- | ------------------- |
| UI components (tables, forms, buttons, modals) | Ant Design          |
| Layout, spacing, flex/grid                     | Tailwind CSS        |
| Theme tokens (colors, border radius)           | Antd ConfigProvider |

Never use Tailwind to override Antd component styles. Never use Antd for layout structure.

### Ant Design SSR setup

Antd uses CSS-in-JS which normally causes a flash of unstyled content in Next.js App Router. `AntdRegistry` (from `@ant-design/nextjs-registry`) fixes this by extracting the CSS during server rendering and injecting it into the HTML before it reaches the browser.

### Theme configuration

The global theme is set in `app/layout.tsx` via `ConfigProvider`:

```typescript
const antdTheme = {
  token: {
    colorPrimary: "#1677ff", // blue — used by buttons, links, active states
    borderRadius: 6, // applied to all Antd components globally
  },
};
```

To change the brand color or any design token, edit this object. It propagates to every Antd component automatically.

### Tailwind v4 setup

Tailwind v4 uses a CSS import instead of a config file:

```css
/* app/globals.css */
@import "tailwindcss";
```

PostCSS is configured in `postcss.config.mjs` to process this import. No `tailwind.config.ts` is needed for standard utility classes.

### Client component requirement

All Antd components must be in files marked `'use client'`. They use browser APIs and React hooks internally. If you use an Antd component in a server component, Next.js will throw an error.

## 8. Route Structure

Next.js App Router uses folder names in parentheses `(name)` as **route groups** — they organize pages without affecting the URL.

```
URL                    Maps to file
/                      app/page.tsx                              → redirects to /dashboard
/dashboard             app/(dashboard)/page.tsx                  → inside dashboard shell
/sign-in               app/(auth)/sign-in/[[...sign-in]]/page.tsx
/sign-up               app/(auth)/sign-up/[[...sign-up]]/page.tsx → redirects to /sign-in
```

### Route group: `(dashboard)`

Every file under `app/(dashboard)/` is automatically wrapped in `app/(dashboard)/layout.tsx`, which renders the `DashboardShell` (sidebar + header). To add a new ERP module:

```
app/(dashboard)/
  products/
    page.tsx        → /products  (list view)
    [id]/
      page.tsx      → /products/123  (detail view)
```

### Route group: `(auth)`

Auth pages use a plain centered layout — no sidebar, no header. They are deliberately outside the `(dashboard)` group so they don't inherit the dashboard shell.

## 9. Dashboard Shell

**`components/layout/dashboard-shell.tsx`** is the persistent chrome around every ERP page: the collapsible sidebar and the top header.

```
┌─────────────────────────────────────────┐
│  ■ IlumeTech ERP           [UserButton] │  ← Header
├──────────┬──────────────────────────────┤
│          │                              │
│ Dashboard│                              │
│ Products │      {page content}          │  ← Content
│ Stock    │                              │
│ Orders   │                              │
│          │                              │
└──────────┴──────────────────────────────┘
  ↑ Sider (collapsible)
```

The `collapsed` state is managed with `useState` inside the shell. The Antd `Sider` handles the collapse animation and icon toggle automatically when you pass `collapsible`.

The `UserButton` in the header is a Clerk component — it shows the user's avatar and opens a dropdown for account management and sign-out.

To add navigation links, edit the `NAV_ITEMS` array in `dashboard-shell.tsx`.

## 10. Environment Variables

Copy `.env.example` to `.env.local` and fill in the values before running the app.

```bash
cp .env.example .env.local
```

| Variable                              | Where to get it            | Purpose                                           |
| ------------------------------------- | -------------------------- | ------------------------------------------------- |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`   | Clerk dashboard → API Keys | Identifies your Clerk app (safe to expose)        |
| `CLERK_SECRET_KEY`                    | Clerk dashboard → API Keys | Server-side Clerk operations (keep secret)        |
| `NEXT_PUBLIC_CLERK_SIGN_IN_URL`       | Set to `/sign-in`          | Clerk's redirect target for unauthenticated users |
| `NEXT_PUBLIC_CLERK_SIGN_UP_URL`       | Set to `/sign-up`          | Clerk's sign-up URL (redirects to sign-in)        |
| `NEXT_PUBLIC_CLERK_AFTER_SIGN_IN_URL` | Set to `/dashboard`        | Where Clerk sends users after login               |
| `NEXT_PUBLIC_CLERK_AFTER_SIGN_UP_URL` | Set to `/dashboard`        | Where Clerk sends users after signup              |
| `NEXT_PUBLIC_API_URL`                 | Your NestJS API URL        | Base URL for all axios requests                   |

Variables prefixed with `NEXT_PUBLIC_` are embedded in the browser bundle. Variables without this prefix (`CLERK_SECRET_KEY`) stay on the server only.

## 11. Data Flow: End-to-End Example

Here's what happens from the moment a user visits `/dashboard` to seeing a table of products:

```
1. Browser hits /dashboard
        ↓
2. middleware.ts runs (edge)
   → Clerk checks for session cookie/JWT
   → Valid session found → request continues
        ↓
3. app/(dashboard)/layout.tsx renders (server)
   → Returns <DashboardShell> with the page as children
        ↓
4. DashboardShell renders (client)
   → Antd Layout, Sider, Header appear
   → UserButton shows the logged-in user's avatar
        ↓
5. ProductsPage renders (client)
   → useQuery({ queryKey: ['products', 'list'], queryFn: productApi.getAll })
   → TanStack Query checks cache: no data yet → triggers request
        ↓
6. productApi.getAll() calls apiClient.get('/products')
        ↓
7. ApiAuthInjector's request interceptor fires
   → Calls getToken() from Clerk → gets a fresh JWT
   → Attaches: Authorization: Bearer eyJhbGci...
        ↓
8. Request reaches NestJS API at NEXT_PUBLIC_API_URL/products
   → ClerkAuthGuard validates the JWT
   → PermissionsGuard checks org:products:read
   → Controller returns { data: [...], meta: { total, page, limit } }
        ↓
9. TanStack Query receives the response
   → Stores it in cache under key ['products', 'list']
   → Re-renders the component with data
        ↓
10. Antd Table renders with the product rows
```
